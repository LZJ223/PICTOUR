# PICTOUR 人机协作与 Git 规范

`dev` 是用户独立的大地图与美术实验分支，从共用 `main` 起步，以可运行、可试玩的小步交付推进 GameJam。用户负责体验判断，agent 负责程序实现、验证、文档和 Git 整理。此分工与原暂不提交偏好于2026-10-08确认；用户于2026-10-09授权将当前积累成果作一次本地基线提交。

我们这一路的目标是设计并搭建完整第一章大地图、验证玩法，并探索程序化与 AI 辅助的唯美治愈童话美术路径，先做 Windows 原型。队友另一路探索关卡式设计，当前尚未上传 GitHub。两路可以独立演进，未来比较成果后再决定复用或整合，不预先要求合并。

## 职责与决定

| 工作 | 已确认责任 |
|---|---|
| 玩法目标、谜题解法、范围和美术方向 | 人类决定，agent 提供实现成本与选项 |
| 程序、公共组件、问题定位和回归验证 | 主 agent 统筹；按文件分配实现责任 |
| 大地图搭建与美术实验 | 用户决定设计与方向，agent 提供可试玩实现和实验结果 |
| 带画面试玩与体验验收 | 用户负责，agent 整理复现步骤与反馈 |
| Git 整理、文档和可复现交付 | 主 agent 负责 |
| 稳定版选择、对外发布与赛事投稿 | 用户明确指令后执行 |

任务已明确时，agent 可直接读取、修改、验证和建立本地开发分支，包括在 dev 中修改继承自 main 的公共系统来验证大地图方案。暂不自动暂存或提交，等产生成果后由用户决定。只在缺失信息影响正确实现或最终外部操作尚无授权时提问，继续推进不依赖该答案的部分。操作是否已获授权按当前会话判断，不机械重复确认。

当人与 agent 同时开发，先说明各自正在编辑的文件。特别是 Godot 中未保存的修改，需要由正在操作编辑器的人主动告知；agent 无法通过磁盘状态识别未保存内容。

## 一次任务的流程

1. **明确结果。** 说明玩家应看到或能完成什么、涉及哪个关卡、什么情况算成功。缺陷任务提供操作步骤、预期与实际结果。
2. **核对起点。** 查看分支、未提交修改、最新相关文档和实际源码。保持他人改动，明确任务文件和依赖。
3. **确定最小方案。** 小任务直接实现；跨模块或有多种玩法解释的任务先给简短方案与验收条件。较大任务在日期日志中记录目标、文件归属、阶段与验证。
4. **实现与验证。** 按文件分工，小步修改。先检查解析和启动，再检查此次改变的行为；有体验要求的内容安排人类试玩。
5. **整合与交付。** 阅读差异，更新说明，按提交偏好保留修改或本地提交。交付行为变化、入口、验证结果、限制和需要试玩的步骤。
6. **验收后推进。** 试玩反馈继续调整当前任务。需要推送、合入稳定分支或投稿时，再执行已获明确授权的操作。

提出任务可以使用下面的格式，简单任务用一句话也可以：

```text
目标：玩家应该能……
场景 / 模块：
预期行为：
复现步骤（缺陷任务）：
范围或不能改动的部分：
验收：
优先级 / 截止：
```

交付至少包含「改了什么、如何检查、验证结果、仍有什么限制」。未试玩、未打包、依赖未实现系统的部分应明确标注。仓库内日志不等于已经对外发布的 TapTap 开发日志。

## 多 agent 与文件归属

主 agent 负责协调和最终整合，子 agent 的任务必须包含允许写入的文件、禁止操作和回报要求。研究和审查可并行；写入任务按文件拆分，不能同时编辑同一 `.gd` 或 `.tscn`。

`System/Global.gd`、`System/System_Controller.gd`、`Component/Object/Layer_Object.gd`、`project.godot` 和总装场景涉及多个系统，由当前任务指定一个写入者。关卡成员编辑自己负责的场景和实例参数；改公共组件会影响所有实例，应由集成人处理并检查原型关卡。

共享工作区的分支切换会影响全部 agent。子 agent 不自行切分支或提交；需要独立分支和 Git 操作时，在隔离 worktree 中工作。新 worktree 只包含指定提交的树，不自动包含未提交的规范或探索成果。当前暂不提交期间优先共享工作区按文件分工；确需 worktree 时，由主 agent 核对并显式传递必要未提交上下文。整合前检查实际 diff、资源路径和 Godot 日志，整合后重复受影响行为的验证。

## 分支与同步

| 分支 | 用途 | 整合要求 |
|---|---|---|
| `main` | 共用项目起点与后续共享基线 | 不直接开发；不假定其已经验收，不自动合入 dev 的实验 |
| `dev` | 用户的大地图、玩法与美术实验路线 | 可修改来自 main 的代码和场景，持续保留本路线进度 |
| `codex/<短任务名>` | 大任务、实验或隔离的 agent 实现 | 从 `dev` 起步，审查和验证后整合到 `dev` |

2026-10-08 建立的 `dev` 起点是远端 `main` 的 `948b7e4`。本地 `main` 保留在 `a6a6279`，比已 fetch 的 `origin/main` 落后三次提交。`dev` 当前没有远端分支或 upstream；首次获授权推送后使用 `git push -u origin dev` 建立跟踪关系。后续新任务从现有 dev 继续，不重新从 main 覆盖探索成果。

平时先查看状态再决定是否同步，不在不明改动上自动 pull。main 的新增提交是否引入 dev，需要检查对大地图路线的影响并按用户意图决定，不机械追随 main。未来 dev 建立远端后，fetch 并检查其差异：获授权且可以快进时用 `--ff-only` 更新；存在分叉时根据提交意图整合，不自动重写共享历史。尚无 `origin/dev` 时，不运行针对它的同步命令。

```powershell
git status --short --branch
git fetch origin
git log --oneline --left-right dev...origin/dev
# 确认工作区干净且可快进后：
git merge --ff-only origin/dev
```

单人顺序任务可以使用 `git switch -c codex/shadow-pool dev` 建立任务分支；它仍使用当前工作区，不是并行隔离。并行任务需要独立 Git 操作时使用 worktree，并处理上述未提交上下文。任务分支先检查相对 dev 的 diff，再验证。能快进时快进；不能快进时按依赖合并并解决冲突，整合后验证。多人共享分支不默认 rebase 或 force push。

远端推送和 `main` 整合属于单独明确的交付动作。当前不自动提交、推送或整合；用户以后给出持续授权时无需每次询问。与队友路线的比较或合并需要实际代码和设计证据，不能推测未上传内容。

## 提交与冲突

提交格式为 `type(scope): 中文简述`。scope 选本次主要模块，例如 `layer`、`player`、`shadow`、`level`、`workflow`。范例：

```text
fix(shadow): 换层后关闭不再使用的影子
feat(level): 增加关卡重开入口
docs(workflow): 建立人机协作与 Git 约定
```

一个提交只解决一个目的，功能与无关格式整理分开。提交前查看完整 diff 和 `git diff --check`，只暂存任务文件，再检查 `git diff --cached`。不使用盲目的全仓库暂存，不把缓存、导出包、凭据或个人路径配置一起提交。

用户于2026-10-09明确授权当前成果一次本地提交到dev，提供姓名与邮箱，使用仓库局部配置；不修改全局身份，不借用旧提交作者。此授权不自动扩展到后续任务的提交或远端推送，后续按明确指令执行。

本次归档以从`948b7e4`积累的绘本箱庭开发基线为一个快照目的，包含当前源码、场景、资源及UID、V7角色、专用布景插件、验证场景、素材原图/提示词/来源与协作说明。保留旧实验以便比较，不纳入`.godot/`、`Exports/`、`Builds/`或导出凭据。最大单个素材约3.25 MiB，当前无需启用LFS。提交前检查具体清单、暂存差异、换行、资源引用和已完成的验证；不盲目全仓库暂存。

冲突先检查双方意图。脚本按行为整合；场景同时检查节点路径、UID、资源引用和实例覆盖。二进制资产不能文本合并，应联系当前责任人选择最终版本。禁止未经授权硬重置、删除未提交文件、自动 stash、直接以 ours/theirs 覆盖全部冲突。

撤销共享提交优先 `git revert` 创建反向提交；撤销工作区修改前识别归属和具体范围，保留可恢复副本。不要以清理工作区为由删除用户数据。

## Godot 资源与格式

- 提交 GDScript、场景、资源、`.gd.uid`、`project.godot` 和原始资产；不提交 `.godot/` 缓存、导出包和导出凭据。
- 保留已有 UID；移动或重命名资源时同步引用并重新导入。不要通过删 UID 或缓存伪装修复引用问题。
- 文本统一 UTF-8 和 LF，GDScript 使用 tab。保持项目已有文件名及标识风格，避免全库重排。
- `CollisionBox` 管实体尺寸，`VisualRoot` 管视觉与点选。搬运与视觉投影现使用世界坐标；已验证白模的总装根节点、Level 与 DepthLayer 仍保持零位置、零旋转、单位缩放。其他父节点变换组合需专项验证。
- 当前入口是两层静态绘本箱庭`Illustrated_Garden_Game.tscn`与完整V7角色；旧Story、纵向折页井、白模与四层原型保留F6。参数可编辑，但改层数、倍率或当前层时应检查所有槽位、碰撞位、无人机和影子，不能只改 Inspector 后就宣称适配完成。
- 二进制资源同一时间由一人编辑。当前已有PNG图集，原图、生成来源和提示词保存在Art；若引入大型源资产，再按实际体积和类型评估 LFS。不要对 `.gd`、`.tscn`、`.tres`、`.uid` 启用 LFS。
- 引入第三方或 AI 资产时记录文件、来源、作者/工具、许可、用途与是否经过人工修改；这些记录用于署名和投稿说明。

导出文件统一放在 `Builds/` 或 `Exports/`。可共享的导出预设可提交，账号信息、签名密钥和导出凭据不可提交。当前没有导出预设，正式打包属于后续任务。

## 验证基线

本机已确认引擎位于 `D:\EpicGames\Godot\4.7.2\Godot_v4.7.2-stable_win64_console.exe`。其他成员可以修改下面的本地变量；引擎路径不写入游戏逻辑。命令在项目根目录执行：

依次检查结果；导入失败时先修复再启动。引擎退出码为零也可能输出运行错误，因此必须阅读日志。headless 检查证明解析和初始化，不能代替带画面的行为测试或目标平台导出测试。

| 变化类型 | 最低验证 |
|---|---|
| 文档、协作格式 | 链接与事实检查、diff 检查 |
| 脚本、场景、输入映射 | 导入、120 帧启动、改变行为的复现与回归 |
| 图层、尺寸、碰撞、相机 | 完整轮换、反向轮换、边界换层、画面连续性与碰撞归属 |
| 无人机与玩家实体 | 地面召唤、空中拒绝、移动边界、身体换层、退出、重复召唤与选中对象释放 |
| 影子 | 投影物体各槽位、换层与完整轮换、不符合条件时关闭、非默认参数 |
| 关卡 | 标准解法、替代/错误操作、关键物体掉落、重开与软锁恢复 |
| 投稿包 | 干净环境启动、实际目标平台操作、退出与重新运行、审核用入口 |

新测试针对可观察行为或真实风险。序章回归使用轻量 Godot 场景，不引入测试框架；需检查有效断言数量，不能让中断后的零断言假通过。验证受限时记录具体未测项，由下一轮试玩或实现补齐。
