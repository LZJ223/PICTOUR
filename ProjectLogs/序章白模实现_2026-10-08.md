# 序章功能白模实现与试玩

2026 年 10 月 8 日，在 dev 中实现三个相连的白模实验片段，验证移动手感与两层物件搬运。F5 入口为 `Prologue_Test_Game.tscn`。完整序章仍需要叙事、播片、正式关卡节奏与美术；此轮先让基本操作和谜题能够实际游玩。

## 已确定的序章规则

序章仅包含玩家层与背景层，玩家固定在玩家层。相机横向跟随，纵向固定在 360，跳跃不会改变物件搬入高度。移动观察产生视差，搬运按当前可见位置与尺寸成立，没有隐藏的对齐角度或单一答案。

物件可以前后往返，以新的站位再次搬入。搬入玩家层后成为固定实体；送回背景后再次受视差影响。树、箱子和桥段使用静态物件，不因重力坠落。搬运目标被地形、物件或玩家身体占用时拒绝，正常贴地接缝允许成立，检查失败保留原状态。

序章不提供整体图层轮换、无人机、影子或挪动自己。先检验观察者站位和物件组合，避免同时引入角色碰撞层切换与额外恢复规则。

## 操作与运动参数

| 操作 | 实现 |
|---|---|
| A / D | 行走，最高 260 像素每秒 |
| 短按 Shift | 小于 0.18 秒，在释放时触发 600 像素每秒冲刺，持续 0.16 秒，冷却 0.4 秒 |
| 长按 Shift | 按下立即向 420 像素每秒奔跑速度加速，释放结束奔跑；0.18 秒只区分释放时是否短冲 |
| Space | 跳跃，初速度 620，重力 1800；继承起跳横向速度，形成走跳、跑跳和冲跳 |
| 左键 | 选择青色顶边物件；再次点击同物件或空白取消 |
| W / S | 移近 / 移远一个图层；空选无动作，边界不循环 |
| R | 重置本段物件与位置，清空选中和运动状态 |
| F1 / F2 / F3 | 进入对应功能片段，用于反复测试 |
| F4 | 显示 FPS、物理频率、最近帧 P95 与最大帧间隔 |

运动使用时间步长，包含 0.1 秒跳跃缓存和离地宽限。冲刺受实体墙体阻挡。恢复时持续按住 Shift 会重新进入长按计时，不要求额外松键。

短冲在释放时触发，是区分短按和长按的当前方案。玩家反馈响应慢后，已去掉奔跑开始前的 0.18 秒等待：按下立即开始加速，时长只用于判断释放时是否触发短冲。

## 三个测试片段

### 移动与跑跳

从出生点向右，跳过两段固定矮台，再跨越 180 像素练习沟。分别体验步行、跑跳和冲跳的距离差异。这一段用于调参数，不承担正式叙事。

### 移树与搬箱登台

F2 出生点位于挡路树左侧。左键选中树，S 将它送入背景，道路开放。

高台顶面为 420，地面为 600，180 像素高差超过正常跳高。背景中有垫脚箱。在玩家 x 约 1980 的站位将箱子 W 搬入，箱子中心约 2188、顶面 510、底面 600。先跳上箱子，再跳上高台，两级高差各约 90 像素。走到高台右侧的黄色机关，前方的门打开。

这是推荐尝试位置，程序不要求站在指定坐标。箱子放得不好，可以 S 送回背景，换位置再搬入；物件或角色占用目标位置时会给出失败提示。

### 拼桥与画室

F3 位于 700 像素断口前。普通冲跳不足以直接跨越。玩家 x 约 2900 时搬入背景桥段，得到中心约 3350、宽 320、顶面 580 的实体平台。用两次跑跳分别到达桥段与右岸。

右岸收集一份墨水，继续进入画室，空画卷显现第一笔。画室建立新的恢复点。R 或跌落只恢复所在段物件，保留本次运行内已经开启的门、墨水与画卷；退出游戏后进度不保留。

## 后续章节的能力安排

玩家挪动自己适合留到后续章节：先掌握物件搬运，再学习角色进入其他碰撞层后有哪些路可以走、怎样返回和怎样恢复。它会同时改变可站立表面、观察锚点和解题起点，适合成为独立的章节主题。

可以按下表逐步扩展，顺序仍可通过原型调整：

| 阶段 | 主要学习内容 |
|---|---|
| 序章 | 玩家层与背景层、单物件搬运、视差组合 |
| 新增近景 | 利用较大倍率，讨论尺寸与高度关系 |
| 新增远景 | 组合更远的物件与路径，扩大观察和搬运范围 |
| 无人机与整体层顺序 | 移动观察锚点、重排整体空间 |
| 挪动自己 | 身体进入其他层，寻找路线并返回 |

章节应聚焦一种新增空间规则。新增能力和新增图层可以分开，避免每章同时引入两套变量；新能力需要新的路和新的谜题来证明价值。未来每章从画室出发，通过弱线性箱庭回路带墨水返回，是地图设计目标，此轮只验证墨水与画卷的最小闭环。

## 实现边界

- `Level` 在进入场景树时初始化 Global 参数；System 校验内容 ID 和槽位唯一性。
- 玩家和物件碰撞位依据固定 `layer_id`；整体轮换后玩家跟随当前槽位的内容层。
- `LayerObject` 使用世界坐标计算投影和跨层换算，实体与视觉代理分开。
- 交互请求在物理更新中执行；选取比较继承后的有效 z，处理失效选择。
- `TransferPlatform` 使用独立静态碰撞与点选代理，可编辑尺寸、颜色和标题。
- 高台机关、恢复点、收集和画卷属于此实验关卡；没有正式章节加载或磁盘存档。
- 旧四层原型仍可单独运行。Page Up 切换无人机，飞行 W/S 不同时搬运身体，旧 Q/E 保留图层操作。原项目 UAV 事件实际绑定 Shift，本轮改为 Page Up，避免与奔跑冲突。
- 影子生命周期和旧 Goal 未扩展；本轮没有制作或接入 AI 美术。

## 验证与人类试玩

核心回归通过实际物理检查输入映射、两层与四层配置、完整轮换、选取、换层连续性、占用拒绝、正常接缝、运动、相机和无人机往返。路线测试加载实际白模，通过真实鼠标和按键输入检查移树、搬箱登台、开门、两次跑跳、收集和恢复。

Godot 4.7.2 的导入、序章和旧原型各 120 帧启动均通过，无引擎错误。核心回归最终为 **103 项检查、0 失败**；实际路线测试完整通过，包含树、箱子两级跳、机关、桥段两次跑跳、墨水、画卷、R 和跌落恢复。旧无人机检查同时覆盖重复召唤、已缩放身体、跨层往返和选中身体释放。

白模已使用本机 Mobile 与 D3D12 渲染检查，中文教学文字与物件尺寸轮廓正常。Windows 导出与正式包尚未验证，操作手感仍由人类试玩验收。

试玩重点：

1. 短冲释放时触发是否自然，长跑和跑跳是否易于控制。
2. 玩家能否理解“站位改变搬入位置”，并主动送回背景再次尝试。
3. 目标被占用的反馈是否清楚，是否容易误选或被提示遮挡。
4. 树、箱子与桥是否允许有趣的替代解法，恢复是否足够省心。
5. 通过白模反馈再确定正式序章节奏与美术表达。

所有修改留在 dev 工作区，未暂存、提交或推送。

## 卡顿与层级辨识诊断

玩家反馈左右移动闪回、整幅画面停顿和 Shift 响应慢后，进行了独立窗口的 D3D12 对照测试。诊断分开处理帧耗时、物理与渲染更新、操作等待和图层视觉线索。

### 实测结果

本机 GPU 为 RTX 5080 Laptop；上轮 Godot 默认屏幕 API 报告 60Hz，用户随后说明使用 240Hz 高刷屏。因此上轮报告值不能作为用户屏幕的硬件上限，须复核窗口所在屏幕和实际运行状态。性能统计取稳定运行中的六秒，不包含后续截图的 GPU 读回开销。

| 对照 | 样本数 | 帧间隔中位 | P95 | 最大 |
|---|---:|---:|---:|---:|
| 修改前独立窗口约 60 FPS | 360 | 16.657 ms | 18.784 ms | 19.327 ms |
| 修改前关闭 VSync 的 144 FPS 对照 | 864 | 6.940 ms | 7.189 ms | 8.082 ms |
| 正式同步修改后的 144 FPS 对照 | 864 | 6.940 ms | 7.242 ms | 7.758 ms |

独立运行未复现长时间停顿，不能据此否定玩家当前播放环境的问题。编辑器内嵌窗口尚未实测。当前日志没有对应脚本错误，尚无白模 CPU 或 GPU 负载不足的证据。

高刷新率下已经复现滚动的台阶感。修改前渲染图中，固定平台边缘的位置出现 `664,664,660,660,660,657...`，同一物理位置会维持两三帧。加入插值后，同一物理帧内的不同渲染帧也能看到平台继续移动。采样中玩家绿色像素中心维持在屏幕 639.5，未复现角色实际回闪，不能把更新过程中读取到的相机偏差当作回闪证据。

### 已落实的调整

人物先移动，System 再更新相机和视差投影，Camera 最后提交物理更新。物理仍为 60Hz，开启插值后由渲染器补足中间画面；没有通过提高物理频率或强制关闭 VSync 来掩盖停顿。传送、恢复、整体轮换和单物件搬运清空相关插值历史，避免重置时产生拖影。项目仍使用 Mobile 与 D3D12。

这一做法遵循 Godot 对插值节点只在物理帧修改变换、传送后重置历史的要求。[物理插值说明](https://docs.godotengine.org/en/4.7/tutorials/physics/interpolation/using_physics_interpolation.html) 不同时间源会导致可见抖动，帧耗时停顿与输入延迟需要分别检查。[抖动与输入延迟说明](https://docs.godotengine.org/en/4.7/tutorials/rendering/jitter_stutter.html)

Shift 原实现等待 0.18 秒后才开始奔跑，从行走加速至完整跑速另需约 0.067 秒，正常 60Hz 下合计约 0.25 秒。现在按下 Shift 当个物理帧就开始奔跑加速，保留短按释放时冲刺和长按释放不冲刺。A/D 的起步与反向加速度仍保留，不能把它们与帧耗时混为一谈。

白模增加按视觉槽位更新的填色、轮廓、顶面及层名。背景降低对比并弱化边缘，玩家层维持清晰实体边界；青色可搬标记和黄红选中反馈保持独立。正式美术可以进一步做空气透视、减少远层细节、软化远层边缘，但程序必须在换层后更新这些线索，不能只靠蓝绿配色或只在 HUD 中显示层名。

### 复查方式

更新后核心回归为 **125 项检查、0 失败**，序章和旧原型启动无错误，完整谜题路线通过。实际 D3D12 渲染确认背景箱出现“背景”标签、薄边界和淡化填色；搬入后会切换为玩家层样式。

F4 显示实际运行的 FPS、物理频率、运行时 SceneTree 插值开关、窗口所在屏幕的系统刷新率、VSync、最近 240 帧的 P95、最慢帧间隔及逻辑耗时。它读取当前窗口的屏幕索引，不再仅查询默认屏幕；未知刷新率和无画面模式不会冒充 60Hz。显示关闭时仍记录近期帧间隔，便于卡顿发生后打开查看。该数值使用墙钟间隔，能记录窗口停顿；画面暂停过久或失焦也会增大最大值。帧间隔表示游戏进程更新间隔，不能保证显示器已经按相同节奏呈现。

下一次复现时先在同一段左右移动，查看 F4，再比较编辑器内嵌与独立窗口。如果 FPS 明显降低或最大帧间隔达到几十到几百毫秒，继续沿实际播放环境调查；若 FPS 稳定，重点比较插值后的滚动和操作手感。独立窗口的结果不能替代用户的体验验收。

本机详细诊断场景、JSON、日志和截图保留于忽略目录 `Exports/`，不进入提交。

### 240 FPS 与 60Hz 物理复核

用户说明 240Hz 屏幕上仍有 jitter 后，再次只读审查更新顺序，并在独立进程中比较开启与关闭插值。正式项目继续保持 60Hz 物理与插值开启，测试进程临时关闭 VSync 并限制到 240 FPS；这些临时开关不会写回项目。

| 对照 | 六秒帧数 | 帧间隔中位 | P95 | 最大 |
|---|---:|---:|---:|---:|
| 240 FPS，插值开启 | 1441 | 4.165 ms | 4.520 ms | 5.409 ms |
| 240 FPS，插值关闭 | 1440 | 4.166 ms | 4.474 ms | 4.914 ms |

开启组的运行时 SceneTree 插值确为 true。性能采样完成后，另取 24 张 GPU 渲染样本：人物中心均为 639.5 像素，静态世界标记与相机前后物理位置按插值比例计算出的预测位置偏差小于 0.5 像素，符合像素栅格化取整。关闭组标记对应当前物理位置。两组帧率相近，说明 FPS 稳定本身不能证明运动已经平滑；须结合实际绘制位置判断。GPU 读回不计入上表帧耗时。

同一物理帧内，相机画布在开启组的 1081／1081 对连续渲染采样间继续移动，关闭组则为 0／1080；最大单帧画布位移分别为约 1.294 和 4.333 像素。这直接区分了渲染中间帧插值与每物理帧重复约四次的位置台阶。

源码复核未发现连续移动时在渲染帧写入变换、关闭节点插值、反复清空插值历史或启用像素吸附。Camera2D 内部在物理帧保存画布变换、渲染帧提交插值画布；背景投影在当前固定倍率与恒等父节点下为线性变换，与插值可交换。没有证据支持为此把正式物理频率强制改成 240Hz。[Camera2D 源码](https://github.com/godotengine/godot/blob/4.7/scene/2d/camera_2d.cpp) [2D 渲染插值源码](https://github.com/godotengine/godot/blob/4.7/servers/rendering/renderer_canvas_cull.cpp)

本轮 Godot 枚举到一块 2560×1600 屏幕，系统报告约 60.0008Hz，测试窗口位于该屏幕。因此上述结果证明 240 FPS 的逻辑和离屏渲染采样正常，尚未验证物理屏幕以 240Hz 呈现，也未复现用户实际播放窗口的抖动。当前 F4 新增运行时插值和当前窗口屏幕信息，须结合用户的内嵌／独立窗口、实际 FPS 与帧间隔继续定位；插值不能补救渲染进程本身只产出 60 FPS 或显示呈现的停顿。

Windows 的只读显卡信息同时报告 NVIDIA RTX 5080 Laptop 当前刷新率 240Hz、Intel Graphics 当前刷新率 60Hz，两者显示尺寸均为 2560×1600；另外存在 GameViewer Virtual Display Adapter，未提供刷新率。工具桌面的 Win32 显示设备枚举未得到活动设备，因此没有取得可靠的完整支持模式列表。上述差异提示测试进程和用户可能经过不同显示路径，不能据 Godot 测试窗口的 60Hz 报告认定用户系统设置错误，也不能将离屏测试视为物理 240Hz 屏幕验收。

此次正式代码仅扩展诊断 HUD；两行信息在 y=606–649，底部消息从 y=652 开始，无重叠。导入与主场景 120 帧启动通过，无引擎错误。未修改运动参数，未提交或推送。

### 用户现场反馈与显示呈现复核

用户在编辑器点击 Play 后反馈：渲染约 60 FPS、物理 60Hz、插值开启、窗口屏幕报告 60Hz，P95 约 19ms、最大约 21ms；人物运动时整幅画面有拉回感。随后补充：录屏进行时肉眼仍然抖动，但录制的视频回放正常。只读查看本机当前游戏进程，启动参数存在 `--wid`，确认它嵌在编辑器窗口中，即使该工作区以浮动窗口显示，也不是完全独立的游戏窗口。

默认 VSync 独立测试中，筛选两帧角色速度均为 260px/s 的恒速区间：60Hz 物理有 292 对有效帧，120Hz 有 359 对，两组均未检测到绘制相机反向或重复位置，相机位置与插值预测误差小于 0.0001px。P95 分别为 19.870／19.331ms；60Hz 组出现一次 90.161ms 峰值，120Hz 组最大 20.921ms。运行次数不足以将该尖峰归因物理频率。非恒速区间角色已停止造成的重复位置已排除，不能作为持续滚动停顿证据。

临时跑跳对照显示，提高到 120Hz 会改变跳跃边界：最高高度约 112.05→109.43px，距离约 301.03→294.03px。这是测试环境的小样本，不是新玩法验收；正式项目继续保持 60Hz 与内建插值，不改物理频率。内建插值启动时自动将运行时 `physics_jitter_fix` 置零，无证据支持二者冲突。[官方设置说明](https://docs.godotengine.org/en/4.7/classes/class_projectsettings.html#class-projectsettings-property-physics-common-physics-interpolation)

目前显示呈现链路的排查优先级上升。屏幕捕获取得数字图像表面，不等于记录面板的扫描和物理响应；录像的抽样也可能遗漏短暂异常，因此录屏正常不能证明渲染和显示全过程正常。F4 与绘制完成回调的采样同样不能测得每张画面最终何时到达物理屏幕。[Microsoft 捕获说明](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) [NVIDIA Rendered／Displayed FPS 说明](https://images.nvidia.com/content/geforce/technologies/frameview/frameview-1-4-user-guide-web-version.pdf)

为定位而新增两个独立试玩入口：`Play_Standalone.cmd` 与 `Play_NoVSync.cmd`。两者都以同一关卡、1280×720、240 FPS 上限启动；第二个仅在该进程关闭 VSync，可能出现撕裂，退出后不改变项目配置或系统设置。先停止编辑器试玩，再依次运行两者，同一区域比较肉眼表现。禁用 VSync 的参数不能覆盖驱动强制同步，系统的可变刷新率状态尚未查明。[Godot VSync 与窗口抖动说明](https://docs.godotengine.org/en/4.7/tutorials/rendering/jitter_stutter.html)

F4 现在自动识别内嵌／独立窗口；仅开启时采样绘制完成后的逻辑画布位置，记录最多 600 帧，不做 GPU 截图读回。同向移动时反向超过 0.05px 才计作回拉，排除方向切换和大幅传送；F7 暂时固定镜头，F4 关闭、R 与切段均恢复跟随。关闭 F4 会把带唯一名称的采样保存到本机 `user://MotionDiagnostics/`，控制台输出完整位置，不覆盖旧采样。计数表示提交给画布的位置，不能检测物理屏幕的扫描或呈现异常。

验证：核心回归 **130 项、0 失败**，新增五项覆盖固定镜头时人物继续移动、恢复跟随以及 R／切段不会留下固定镜头。实际 D3D12 交互验证中，固定镜头后人物前进 83.33px、相机位移为零；恢复后偏差为零，保存 53 个绘制样本成功。诊断 HUD 两行仍在 y606–649，底部消息从 y652 开始，无重叠。主场景导入和 120 帧启动通过；新增诊断不构成抖动已经解决的结论。

用户随后提供约 7.67 秒、229 帧、约 29.87 FPS 的手机拍屏视频。抽帧可见挡路树的长竖边在部分画面中出现分段横移，例如第 0 帧以及约 1.91 秒的第 57 帧；该白模物件实际为矩形。此现象符合扫描时序／撕裂样式，但手机滚动快门也可能令屏幕运动分段，不能单凭约 30 FPS 的拍屏认定显示器或驱动故障。[滚动快门逐行曝光说明](https://docs.baslerweb.com/electronic-shutter-types) 视频与抽帧分析保留在忽略目录，未改原视频。

进一步以固定 HUD 特征估计手机平移、旋转和尺度，匹配残差中位约 0.083px、P95 约 0.147px。校正手持晃动后，树两侧仍在局部高度出现同向台阶：第 60 帧约 y435 处约 18px，固定 HUD／边框没有对应台阶。逐行检测有 94／229 帧包含超过 6px 的错位候选；这是拍屏候选数，不能当作游戏故障帧计数。文件约 0.67Mbps，压缩、手机逐行曝光与屏幕刷新混叠均需保留；视频包含左右反向、跳跃等操作，不能据整段轨迹的方向变化证明相机逻辑回拉。现有证据支持优先进行显示呈现对照，尚未确定故障环节。

### 独立窗口对照结论与当前默认配置

用户完成同区域肉眼对照，确认当时的 `Play_NoVSync.cmd` 顺滑，`Play_Standalone.cmd` 则存在整幅画面抖动。两次运行采用同一关卡、1280×720 与 240 FPS 上限，差别是关闭／开启 VSync；物理均为 60Hz，插值均开启。结合此前正常的绘制轨迹，问题范围缩小到本机开启同步时的帧率或呈现节奏。禁用同步同时会解除同步带来的渲染帧率限制，因此尚不能区分限制到约 60 FPS 的影响、驱动同步与实际显示链路，更不能断言 VRR 或显卡驱动故障。

据此将 Windows 原型的项目默认改为 `window/vsync/vsync_mode=0`、`run/max_fps=240`。物理继续保持 60Hz，人物、相机、投影与插值逻辑未因本次对照改变。配置需停止旧游戏后重新运行才生效；独立窗口的人类验收不能代替更新后编辑器内嵌窗口的验收。关闭同步可能出现撕裂，其他设备的体验仍须单独验证。[Godot 同步设置说明](https://docs.godotengine.org/en/4.7/classes/class_projectsettings.html#class-projectsettings-property-display-window-vsync-vsync-mode)

现在 `Play_Standalone.cmd` 采用关闭同步的新默认，`Play_NoVSync.cmd` 保留显式关闭同步的同配置入口；需要开启同步复查时使用新增的 `Play_VSync.cmd`。该入口加载 `Tests/VSync_Comparison.tscn`，在同一白模与帧率上限下临时开启当前窗口同步，退出不写回项目配置。此处更新取代上节“两个旧启动器只相差同步开关”的历史操作说明。

本轮导入、主场景与旧四层原型各 120 帧启动通过，核心回归 **130 项、0 失败**，实际树、箱子登台、机关门、拼桥跑跳、收集、画卷与恢复路线完整通过，日志无引擎错误或警告。Windows／D3D12 原生进程另验证普通与同步对照场景各 120 个物理帧：实际 VSync 分别为 0／1，两者帧率上限 240、物理 60Hz、运行时插值开启，退出码均为零且错误日志为空。该检查验证设置生效，不是肉眼显示验收。修改继续保留在 dev，未暂存、提交或推送。

用户随后确认更新后编辑器内嵌窗口也无抖动。当前关闭同步、渲染上限 240 FPS、物理 60Hz 与插值开启的配置已通过本机独立和内嵌两种窗口的肉眼试玩，后续进入美术实验。具体同步问题的底层原因仍未确定，其他设备需另行验收。
