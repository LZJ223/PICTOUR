# PICTOUR 关卡设计与协作指南

> 适用对象：关卡策划、关卡美术及协作开发者  
> 记录日期：2026-10-06  
> 适用版本：当前 `PICTOUR` 白模项目

## 1. 这份文档解决什么问题

本文用于帮助关卡策划快速理解当前项目，并完成以下工作：

- 在 Godot 中找到关卡相关文件；
- 基于现有关卡创建新关卡；
- 在不同图层中摆放地面和物品；
- 正确配置可转换物品；
- 向程序提出新增物品类型的需求；
- 完成关卡自测和交付。

本文只介绍关卡制作所需内容，不要求关卡策划理解完整程序架构。

## 2. 项目架构概述

当前游戏由四个“内容层”组成。每个内容层都拥有自己的地面、物品和独立碰撞关系。

内容层本身具有固定身份，但它在画面中所处的前后位置可以循环变化。玩家始终与当前活动层发生物理碰撞，其他层主要作为远近不同的画面和解谜空间存在。

一个运行中的关卡可以简单理解为：

```text
游戏总场景
├─ 关卡
│  ├─ Layer0：地面与物品
│  ├─ Layer1：地面与物品
│  ├─ Layer2：地面与物品
│  └─ Layer3：地面与物品
├─ 玩家
├─ 相机
└─ 系统控制器
```

需要记住的核心规则只有三条：

1. 每个物品必须属于某个 `Layer`。
2. 摆放物品时修改物品根节点的位置，不要修改其 `VisualRoot`。
3. 四个 Layer 的名称、编号和初始槽位必须保持唯一且完整。

## 3. 文件组织逻辑

```text
PICTOUR/
├─ Prototype_Game.tscn          # 当前游戏运行入口
├─ project.godot                # 项目设置和按键配置
├─ Level/
│  └─ Prototype_Level.tscn      # 原型关卡，可作为新关卡模板
├─ Component/
│  ├─ Layer/
│  │  └─ Layer.tscn             # 单个内容层模板
│  ├─ Object/
│  │  ├─ Box/                   # 方块物品
│  │  ├─ Ground/                # 地面
│  │  ├─ Goal/                  # 目标物品
│  │  └─ Player_Object/         # 无人机模式下留下的玩家实体
│  └─ Player/                   # 玩家场景与移动脚本
├─ System/                      # 全局输入与图层系统，不属于关卡编辑范围
└─ ProjectLogs/                 # 项目说明与协作文档
```

关卡策划通常只需要编辑：

- `Level/` 中自己负责的关卡场景；
- 关卡场景内各个 Layer 下的物品实例；
- 必要时调整某个实例在检查器中的公开参数。

以下文件通常不要由关卡策划直接修改：

- `project.godot`；
- `System/` 下的脚本；
- `Component/` 下的公共模板和脚本；
- `Prototype_Game.tscn` 原文件。

如果公共物品行为不符合关卡需求，应先记录需求并交给程序修改公共模板，避免某一关出现只对本关生效的隐藏改动。

## 4. 四个图层怎样工作

### 4.1 内容层

当前关卡固定使用四个内容层：

| 节点名 | 固定 layer_id | 默认初始 slot | 初始作用 |
|---|---:|---:|---|
| `Layer0` | 0 | 0 | 最前方槽位 |
| `Layer1` | 1 | 1 | 当前玩家活动槽位 |
| `Layer2` | 2 | 2 | 中后方槽位 |
| `Layer3` | 3 | 3 | 最后方槽位 |

游戏过程中四层会循环换位，因此 `Layer0` 不会永远显示在最前方，`Layer1` 也不会永远是玩家当前所在的内容层。

`layer_id` 表示内容层身份，不应在运行过程中改变；`slot` 表示当前画面前后位置，会由系统改变。

### 4.2 显示倍率

四个槽位当前使用以下倍率：

```text
FRONT   约 1.333
CURRENT 1.0
MIDDLE  0.75
BACK    0.5625
```

越靠后的物体显示越小，随玩家移动产生的画面位移也越慢。关卡策划不需要手动制作这种视差，系统会根据物品所属 Layer 自动计算。

### 4.3 物理碰撞

四个内容层拥有分开的碰撞关系。玩家只与当前活动内容层碰撞。图层轮换时，系统会自动改变玩家所在的碰撞层。

请不要在关卡实例上手动调整 `collision_layer` 或 `collision_mask`。这些值由图层系统维护，手动覆盖容易造成玩家站在不可见地面上、穿过方块或同时碰撞多个层。

## 5. 如何创建一个新关卡

### 5.1 创建关卡文件

推荐从原型关卡复制，而不是从空场景开始：

1. 在 Godot 的 FileSystem 面板中找到 `Level/Prototype_Level.tscn`。
2. 复制该场景。
3. 将副本保存在 `Level/` 下。
4. 使用清晰的英文文件名，例如：

```text
Level_01_Introduction.tscn
Level_02_Alignment.tscn
Level_03_UAV.tscn
```

5. 打开新场景，确认根节点下仍然存在 `Layer0`、`Layer1`、`Layer2`、`Layer3`。

不要直接覆盖 `Prototype_Level.tscn`，它应继续作为模板和基础验证关卡使用。

### 5.2 检查图层配置

新关卡中的四层应满足：

| 节点 | layer_id | slot |
|---|---:|---:|
| Layer0 | 0 | 0 |
| Layer1 | 1 | 1 |
| Layer2 | 2 | 2 |
| Layer3 | 3 | 3 |

每个编号只能出现一次。不要删除某一层，也不要增加第五层；当前系统、显示倍率和碰撞位均按四层设计。

### 5.3 编辑地面

每个 `Layer` 默认带有一个 `Ground`。

当前原型地面结构为：

```text
Ground
├─ CollisionPolygon2D    # 玩家和物品实际站立的碰撞面
└─ VisualRoot
   └─ Polygon2D          # 画面中看见的地面
```

如果只移动整块地面，应选择 `Ground` 根节点并修改 `position`。

如果要改变地形轮廓，需要同时修改：

- 根节点下的实体碰撞多边形；
- `VisualRoot` 下的显示多边形。

两者轮廓必须一致，否则会出现“看得见但踩不到”或“看不见但撞得到”的区域。

地面默认不可转换图层，不要开启其转换能力。

### 5.4 放置物品

以方块为例：

1. 在 FileSystem 中找到 `Component/Object/Box/Box.tscn`。
2. 将其拖入目标 `Layer` 节点下。
3. 选中方块的根节点。
4. 修改根节点的 `position` 完成摆放。
5. 保持 `VisualRoot.position = (0, 0)`、`VisualRoot.scale = (1, 1)`；运行时系统会自动更新它们。

正确结构：

```text
Layer2
├─ Ground
├─ Box
├─ Box2
└─ Goal
```

不要把物品放在 `VisualRoot`、`Ground` 或其他物品下面，也不要额外创建普通 Node 作为 Layer 的直接子节点。

### 5.5 放置刚体时避免初始穿插

`Box` 是 `RigidBody2D`，运行后会受重力和碰撞影响。摆放时应注意：

- 不要让方块与地面重叠；
- 不要让两个方块互相重叠；
- 不要把方块贴得过近，给物理解算留出少量余量；
- 需要堆叠时，从稳定、低重心的结构开始验证；
- 每次调整地形后重新运行，观察方块是否在开场瞬间弹起或滑落。

当前标准方块为 `40 × 40`。原型地面顶面位于世界坐标约 `y = 520`，因此标准方块中心放在 `y = 500` 时恰好落在地面上。新地形应根据实际碰撞轮廓重新计算摆放高度。

### 5.6 设置出生点

玩家目前不保存在 `Level` 场景中，而是在游戏总场景 `Prototype_Game.tscn` 中。

这意味着新关卡文件本身暂时没有独立出生点数据。若新关卡需要不同出生点，应在交付说明中明确提供：

```text
玩家出生位置：Vector2(x, y)
初始面向：左 / 右
初始活动层：默认 Layer1 / 其他需求
```

由程序或负责总装场景的成员建立该关卡对应的运行场景，并设置玩家位置。

### 5.7 建立关卡测试入口

当前项目没有自动关卡加载器，主场景固定引用 `Prototype_Level.tscn`。测试新关卡时，推荐为关卡制作单独的测试总装场景：

1. 复制 `Prototype_Game.tscn`，不要覆盖原文件。
2. 使用与关卡一致的名称，例如：

```text
Level_01_Introduction_Test.tscn
```

3. 将其中原有的 `Level` 实例替换为新关卡。
4. 新关卡实例仍命名为 `Level`。
5. 确认 `System` 中的四个 Layers 引用仍分别指向：

```text
Level/Layer0
Level/Layer1
Level/Layer2
Level/Layer3
```

6. 设置该关卡的玩家出生位置。
7. 使用“运行当前场景”进行测试。

如果团队决定由程序统一维护测试入口，关卡策划只需提交关卡场景和出生点说明，不必自行制作测试总装场景。

## 6. 现有物品怎样使用

### 6.1 Box

Box 是可受重力影响、可推动、可被选择并可转换图层的方块。

关卡用途包括：

- 作为踏脚平台；
- 堵住或打开通路；
- 通过图层转换改变实际尺寸；
- 通过图层轮换改变画面对齐关系。

摆放时只修改根节点位置。除非有明确验证结果，不要直接修改根节点比例、碰撞比例或碰撞组。

### 6.2 Ground

Ground 是每层的固定静态地面，不可转换图层。它同时承担该层的主要视觉基底和实体碰撞。

### 6.3 Goal

当前 Goal 场景具有目标物体的外形，但尚未形成完整的通关判定流程。并且当前 `Goal.tscn` 实际引用的是 Box 脚本。因此在程序修正和补充胜利逻辑前，不要把“接触 Goal 后自动通关”作为已实现功能。

使用 Goal 设计关卡时，应在交付说明中写清楚预期触发方式，例如：

- 玩家身体接触；
- 玩家进入指定范围；
- 将某个方块送到 Goal；
- Goal 与玩家处于同一内容层；
- 满足多个条件后激活。

### 6.4 Player_Object

该对象由无人机系统自动生成，用来保留玩家身体。关卡策划不需要手动将它放入关卡。

## 7. 如何增加物品

“增加物品”分为两种情况，两者工作量完全不同。

### 7.1 增加现有物品的实例

如果只是希望关卡中多一个 Box 或 Goal：

1. 从 FileSystem 将对应 `.tscn` 拖入目标 Layer。
2. 修改根节点位置。
3. 为实例使用易读名称，例如 `Box_Start`、`Box_Bridge`、`Goal_Exit`。
4. 运行并验证其初始稳定性、选择范围和跨层行为。

这种操作不需要创建新脚本。

### 7.2 增加全新的物品类型

如果物品拥有新的外观、碰撞形状或交互行为，应建立新的公共物品类型。建议由关卡策划先提交需求，再由程序完成组件模板。

关卡策划应提供以下信息：

```text
物品名称：
用途：
初始尺寸：
物理类型：静态 / 可推动 / 自主运动 / 触发区域
能否被玩家选择：是 / 否
能否转换图层：是 / 否
转换图层后是否改变实际尺寸：是 / 否
是否受重力影响：是 / 否
是否能压住按钮或阻挡玩家：是 / 否
触发条件：
触发结果：
是否需要保存状态：
所需视觉反馈：
所需声音反馈：
示意图或参考：
```

程序侧新增物品时，文件应放在：

```text
Component/Object/物品类型名/
├─ 物品类型名.tscn
└─ 物品类型名.gd
```

标准节点结构建议保持为：

```text
物理根节点
├─ 实体碰撞
└─ VisualRoot
   ├─ 物品外观
   ├─ 选中轮廓（如可选）
   └─ Area2D
      └─ 点选形状（如可选）
```

新物品交付给关卡策划前，程序侧至少应确认：

- 可以直接拖入任意 Layer；
- 运行时不会报错；
- 图层轮换后视觉位置正确；
- 可转换物品跨层后位置和尺寸正确；
- 实体碰撞和画面轮廓一致；
- 可选物品的鼠标区域与画面一致；
- 不可选物品不会被误选；
- 不需要关卡策划手动配置碰撞位。

## 8. 关卡设计建议

### 8.1 先设计状态，再摆放物体

一个图层谜题通常不只有“初始画面”，而是包含多个轮换状态。设计前建议先画出状态表：

| 操作次数 | 当前活动内容层 | 关键对齐关系 | 玩家目标 |
|---:|---|---|---|
| 0 | Layer1 | 初始状态 | 找到可操作物体 |
| 1 | 另一内容层 | 平台与出口对齐 | 到达新区域 |
| 2 | 另一内容层 | 方块尺寸改变 | 打开通路 |

实际内容层会循环变化，不能只检查初始画面是否合理。

### 8.2 明确哪些变化是视觉，哪些是物理

- 整体轮换图层：物体实际世界状态不变，画面前后关系改变，玩家切换碰撞内容层。
- 单个物体转换图层：物体会更换所属内容层，并改变真实位置和实际尺寸等级。

设计谜题时应明确玩家是在利用视差对齐，还是在真正改变某个物体的物理状态。

### 8.3 给玩家可读的信息

同一物品在不同深度下会产生明显大小变化。关卡中应提供稳定参照物，例如：

- 不可移动的门框；
- 每层颜色或明度区别；
- 重复出现的地面标记；
- 明确的目标轮廓；
- 能表现当前活动层的反馈。

不要只依赖轻微的色差表达关键谜题状态。

### 8.4 避免无解状态

对于能够移动或掉落的刚体，需要检查：

- 是否可能掉出所有可达区域；
- 是否可能卡入墙体；
- 是否可能被放大后堵死唯一通道；
- 是否能在错误图层中永久失去选择机会；
- 玩家是否能在没有重置功能时恢复谜题。

如果存在软锁风险，应在需求中注明需要重置点、自动回收区域或关卡重开功能。

### 8.5 控制首屏信息量

新机制首次出现时，建议每次只引入一个变量：

1. 先让玩家理解整体图层轮换；
2. 再引入物体选择；
3. 再引入单个物体转换与尺寸变化；
4. 最后组合无人机、刚体和多步骤对齐。

## 9. 编辑时最常见的错误

### 错误一：移动了 VisualRoot

结果：编辑器中看起来位置正确，运行后物品被系统再次偏移。

处理：恢复 `VisualRoot` 的默认局部位置和比例，只移动物品根节点。

### 错误二：物品没有放在 Layer 下

结果：运行时无法找到所属图层，可能触发断言或无法参与轮换。

处理：将物品实例直接放到 `Layer0～Layer3` 之一的下面。

### 错误三：修改碰撞层或遮罩

结果：玩家与错误图层碰撞，或完全无法碰撞。

处理：恢复公共场景默认配置，让系统自动设置。

### 错误四：只改外观，没有改实体碰撞

结果：画面轮廓与实际碰撞不一致。

处理：修改地形或新物品形状时同时维护视觉和实体碰撞。

### 错误五：在 Layer 下加入普通辅助节点

结果：当前视觉刷新会尝试把它当成图层物体调用，可能运行时报错。

处理：Layer 的直接子节点只放标准图层物体。辅助节点应放到关卡根节点下，或先让程序提供安全容器。

### 错误六：直接修改公共 Component 场景

结果：其他关卡中的所有同类物品一起变化。

处理：仅调整关卡内实例公开参数；涉及公共行为时先与程序确认。

## 10. 关卡自测清单

### 基础结构

- [ ] 关卡根节点下存在 Layer0、Layer1、Layer2、Layer3。
- [ ] 四层的 `layer_id` 分别为 0、1、2、3。
- [ ] 四层初始 `slot` 分别为 0、1、2、3。
- [ ] 所有图层物品都直接属于某个 Layer。
- [ ] 没有把 Player_Object 手动放入关卡。

### 视觉与碰撞

- [ ] 四层轮换一整圈后能回到初始画面状态。
- [ ] 玩家只与当前活动内容层碰撞。
- [ ] 地面外观与碰撞轮廓一致。
- [ ] 方块开场时不会弹起、穿模或意外滑落。
- [ ] 物品在各槽位下没有明显跳帧或错误偏移。

### 物品转换

- [ ] 可选物品能够用鼠标正确选中。
- [ ] 重叠物品会优先选中画面最前方的一个。
- [ ] 选中轮廓与物品画面位置一致。
- [ ] 物品只能转换到合法相邻槽位。
- [ ] 转换后的尺寸、位置和碰撞符合谜题设计。
- [ ] 地面等不可转换物品不会被转换。

### 流程与容错

- [ ] 玩家出生时不会卡在碰撞体中。
- [ ] 正常解法可以完成全部步骤。
- [ ] 反向操作和重复轮换不会破坏关卡。
- [ ] 关键刚体掉落后仍可恢复，或已有明确重置方案。
- [ ] 无人机开启和关闭后玩家位置、图层与碰撞正常。
- [ ] 不存在玩家永久无法返回的软锁区域。

## 11. 关卡交付规范

每个关卡建议提交以下内容：

```text
关卡场景：Level/Level_XX_Name.tscn
测试场景：Level/Level_XX_Name_Test.tscn（若团队要求）
关卡说明：目标、机制、标准解法
出生信息：玩家坐标和初始状态
新增需求：物品、触发器、反馈或系统功能
已知问题：无法避免的物理问题或临时方案
```

关卡说明至少应包含：

1. 本关教学或考察的核心机制；
2. 玩家初始可见信息；
3. 标准解法的操作顺序；
4. 允许的替代解法；
5. 已测试的错误操作；
6. 通关触发条件；
7. 是否依赖尚未完成的程序功能。

推荐命名方式：

```text
场景文件：Level_序号_英文名称.tscn
图层物品：类型_用途或位置

示例：
Level_01_Introduction.tscn
Box_Start
Box_Bridge
Goal_Exit
```

## 12. 当前版本限制

关卡策划在设计前应了解以下现状：

- 当前固定为四个图层，不支持关卡自行改变层数。
- 主场景固定引用原型关卡，尚无完整关卡选择或自动加载流程。
- 玩家出生点尚未作为关卡数据保存在 Level 场景中。
- Goal 尚未形成可依赖的完整通关逻辑。
- Layer 的直接子节点必须是实现了图层视觉接口的标准物品。
- 刚体行为会受初始重叠、堆叠结构和地形斜率影响，需要实际运行验证。
- 当前白模主要使用 Polygon2D 和基础碰撞，正式美术资源接入方式尚未在关卡层确定。
- 如果更改公共 Component，所有使用该组件的关卡都可能受到影响。

发现以上限制影响关卡设计时，应先提交明确需求，不要在单个关卡中制作临时脚本绕开系统。
